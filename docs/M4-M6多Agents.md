# M4–M6 主对话持续开发手册

更新时间：2026-09-06  
适用仓库：`langyashan-defense`  
目标：从当前 M4 状态继续推进到 M5、M6，并且**默认只使用一个主对话大模型顺序开发**，不再鼓励多 Agents 并发推进。

> 这是一份给“主对话”的执行手册，不替代 `AGENTS.md`、`docs/PRD.md`、`docs/COLLAB.md`、`docs/MILESTONES.md` 和 `docs/OPEN-QUESTIONS.md`。发生冲突时，按 `AGENTS.md` → `docs/PRD.md` → `docs/COLLAB.md` → `docs/MILESTONES.md` 的顺序执行。

---

## 1. 当前进度快照

以 `docs/MILESTONES.md` 为准，当前状态是：

- M0：已完成
- M1：已完成
- M2：已完成
- M3：已完成
- M4：进行中
- M5：未开始
- M6：进行中

也就是说，项目不是从头重来，而是要在**已有可玩基础上收口 M4、再推进 M5，最后完成 M6**。

---

## 2. 本阶段总原则

### 2.1 只保留一个主对话

- 默认**不启动并发 Agents**。
- 不要为了“看起来更快”而把任务拆成多个并行对话。
- 当前主对话负责：读文档、改代码、跑验证、更新里程碑、整理结论。
- 只有在主对话明确判断“此步骤无法继续”时，才考虑是否需要额外支持；而且必须先停下来确认，不要自动并发。

### 2.2 一次只推进一个明确小步骤

每轮只做一件事：

1. 识别当前最小可交付目标；
2. 修改对应文件；
3. 运行验证；
4. 记录结果；
5. 再进入下一步。

禁止把 M4、M5、M6 混成一个超大批次一起做。

### 2.3 保持可验证、可回滚、可提交

- 每个小步骤都要能独立验证。
- 不要一次改太多文件，避免失控。
- 任何时候都不要为了并发而牺牲可读性和稳定性。

---

## 3. 开工前固定动作

每次开始工作，先按这个顺序检查：

```bash
uname -a
git status --short --branch
git pull --rebase origin main
node tools/verify-config.js
```

补充要求：

- 如果 `git pull --rebase` 因本地未提交改动失败，先保留现场，辨认改动归属，再继续；不要 `reset --hard`，不要 `push --force`。
- 继续开发前，重新读取 `AGENTS.md`、`docs/PRD.md`、`docs/COLLAB.md`、`docs/MILESTONES.md`。

---

## 4. 当前推进顺序

### 4.1 先收口 M4

M4 的目标不是“再开一堆新工作”，而是把已经接上的美术和表现层做成可展示、可验收版本。

优先顺序：

1. 角色 Billboard、接地、朝向、对象池复用问题；
2. 准心和摄像机输入问题；
3. 第一人称枪械构图与后坐表现；
4. 程序化场景视觉；
5. HUD、音效和加载稳定性；
6. 浏览器实测与里程碑回写。

### 4.2 再推进 M5

M5 重点是联机闭环，不是单纯把“能连上”当完成。

优先顺序：

1. 创建 / 加入房间；
2. 五席与真人 / AI 顶替规则；
3. 真人状态同步；
4. 断线重连与超时接管；
5. 反作弊与多人结算；
6. 联机验收与里程碑回写。

### 4.3 最后收口 M6

M6 重点是打磨和发布准备。

优先顺序：

1. 性能和首屏；
2. 资源体积与加载失败提示；
3. 网络异常与恢复；
4. 结算页和体验细节；
5. `docs/DEPLOY.md`、`docs/MILESTONES.md`、`docs/OPEN-QUESTIONS.md` 的同步更新；
6. 最终验收记录。

---

## 5. 这一阶段不再采用的方式

以下做法在本阶段都不推荐：

- 同时启动多个 Agents 并发推进同一条开发链；
- 让不同对话同时改同一批文件；
- 把一个里程碑拆成很多互相等待的小 Agent；
- 先开大计划、后面再补执行细节；
- 为了“节省时间”跳过验证；
- 为了“先做完”而让主对话外的并发步骤抢占上下文。

如果后续真要恢复并发机制，必须先由主对话单独更新本文件，再由 watson 明确确认，不要默认恢复。

---

## 6. 验证与交付要求

每个小步骤至少要做与改动相匹配的验证。

常用命令：

```bash
node tools/verify-config.js
cd server && npx tsc --noEmit
cd client && npx tsc --noEmit
node tools/check-ws.js ws://127.0.0.1:8081/ws
```

如果改到构建、部署或浏览器表现，还要补充：

- 实际浏览器打开验收；
- 关键截图或控制台结果；
- 资源体积、FPS、首屏等实测。

### 完成判据

- 不能只写“看起来差不多”；
- 不能只跑编译不做实测；
- 不能把未验证内容写成已完成。

---

## 7. 文档同步要求

每次完成一个阶段性目标，都要同步更新：

- `docs/MILESTONES.md`
- 必要时更新 `docs/OPEN-QUESTIONS.md`
- 必要时更新 `docs/DEPLOY.md`

规则是：

- 只写自己已经实测过的内容；
- 不要把推测当完成；
- 不要因为当前只用一个主对话，就省略里程碑记录。

---

## 8. 这份文档的使用方式

主对话按下面节奏持续推进即可：

1. 先看当前状态；
2. 选一个最小任务；
3. 改一个小块；
4. 验证；
5. 记录；
6. 再继续下一块。

**核心原则只有一句：主对话单线推进，先完成一个，再开始下一个。**
