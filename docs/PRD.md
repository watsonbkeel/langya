## 1. 项目概述

### 1.1 一句话定义

一款基于 Cocos Creator 的 **2.5D 网页固守射击游戏**，玩家扮演狼牙山五壮士之一，与 4 名 AI 队友并肩坚守制高点，在 5 分钟内抵御四波共 200 名日军的进攻，以存活为胜利、以歼敌数争 MVP。

### 1.2 立项背景

- 本项目属于「AI+历史」游戏创作课程体系，与已有的「九一八事变北大营」「四行仓库保卫战」共用美术资产管线（军服素材已明确标注为三款游戏共用）。
- 既是可对外发布的作品，也是课程教学案例，因此**代码可读性与工程规范优先级高于炫技**。

### 1.3 目标用户

| 维度 | 说明 |
|---|---|
| 主要用户 | 9–15 岁青少年学员及其家长 |
| 次要用户 | 课程教学场景中的演示观众 |
| 使用环境 | PC 浏览器为主（Chrome / Edge），横屏；移动端浏览器为兼容目标 |
| 单局时长 | 5 分钟（硬性） |

### 1.4 设计原则（不可违背）

| 原则 | 具体要求 |
|---|---|
| 历史尊重 | 表现英雄坚守与牺牲精神，不做猎奇化、不做血腥特效 |
| 适龄合规 | 无血液、无残肢、无仇恨符号、无侮辱性命名；敌方统一称「日军」，不使用蔑称 |
| 阵营固定 | 玩家**只能**加入中国军队，日军**仅由 AI 控制**，不提供任何扮演日军的入口 |
| 教学友好 | 数值可配置、模块边界清晰、关键逻辑有中文注释 |

### 1.5 明确不做的事（v1.0 范围外）

- 不做玩家扮演日军 / 阵营选择
- 不做付费、抽卡、皮肤商城
- 不做角色升级、装备掉落、赛季系统
- 不做语音聊天（仅提供预设快捷短语）
- 不做原生 App 打包（v1.0 只出 Web 版）

## 2. 核心玩法设计

### 2.1 玩法一句话

**居高临下的固守塔防式射击**：玩家在山顶阵地，敌人从山下沿多条路线向上冲锋，玩家用步枪点杀 + 重机枪火力压制，撑满 5 分钟即胜利。

### 2.2 单局流程

```
进入大厅 → 单人开局(自动配4名AI队友) 或 联机房间(最多5人) → 战前10秒部署期
   ↓
第一波：30人（0:10 - 1:15）
   ↓ 间歇 12 秒（补给投放）
第二波：50人（1:27 - 2:32）
   ↓ 间歇 12 秒（补给投放）
第三波：60人（2:44 - 3:52）
   ↓ 间歇 12 秒（补给投放）
第四波：60人（4:04 - 5:00）
   ↓
5:00 时间到 → 结算：存活即胜利 → MVP 评选 → 战报
```

### 2.3 日军兵力编成（已确认）

**日军总兵力 200 人，分 4 批投入**：

| 波次 | 兵力 | 累计 | 战术定位 |
|---|---|---|---|
| 第一波 | 30 人 | 30 | 试探进攻，节奏慢，作为教学引导波 |
| 第二波 | 50 人 | 80 | 加入轻机枪火力组，开始多路并进 |
| 第三波 | 60 人 | 140 | 全线压上，三路同时进攻 |
| 第四波 | 60 人 | 200 | 最后总攻，突击兵比例提升 |

**滚动投放规则**：每波不一次性生成，按小队分批进场，避免浏览器端渲染压力。

| 波次 | 小队规模 | 投放间隔 | 小队数 |
|---|---|---|---|
| 第一波 | 10 人 | 15 秒 | 3 |
| 第二波 | 12 人 | 12 秒 | 4~5 |
| 第三波 | 15 人 | 12 秒 | 4 |
| 第四波 | 15 人 | 10 秒 | 4 |

**同屏存活上限 40 人**：达到上限时暂缓下一小队投放，直到场上敌人减少。这保证了 200 人总量能打完，同时帧率不崩。

### 2.4 五壮士编成：真人 + AI 队友混合

**核心规则：阵地永远是 5 个人，空位由 AI 队友补齐。**

| 场景 | 真人 | AI 队友 | 说明 |
|---|---|---|---|
| 单人模式 | 1 | 4 | **v1.0 主要形态**，开局自动配齐 |
| 2 人联机 | 2 | 3 | |
| 5 人联机 | 5 | 0 | 满编 |

**为什么必须有 AI 队友**：战场设计了三条进攻路线（见 4.2），单人无法同时看住三条路。若不配队友，单人模式要么被背面路线偷家，要么就得砍掉多路线设计。**配 AI 队友既保住了关卡设计，又让单人和联机共用同一套战场逻辑，不需要写两套平衡。**

### 2.5 AI 队友设计

**AI 队友与玩家同属中国军队，使用相同的角色素材与武器。**

| 属性 | 数值 | 说明 |
|---|---|---|
| 生命值 | 100 | 与玩家一致 |
| 武器 | 中正式步枪 | 固定，不切换 |
| 命中率 | 55% | 见下方能力标定 |
| 射速 | 0.7 发/秒 | 略低于玩家手动射速 |
| 血包 | 1 个 | 低于 30% HP 时自动使用 |
| 阵亡 | 不复活 | 与玩家规则一致 |

**能力标定原则**：AI 队友是**协防者，不是代打**。

- 单个 AI 队友的歼敌效率约为熟练玩家的 **50%~60%**
- 4 个 AI 队友合计约能承担全场 **40% 左右**的歼敌量，剩余 60% 需要玩家完成
- AI 队友**不使用重机枪**，重机枪是玩家的专属高价值资源
- AI 队友**不抢空投血包**，空投只给真人玩家

**行为逻辑**：

| 行为 | 规则 |
|---|---|
| 站位 | 开局自动分配到三条路线的防守位，玩家不占的位优先补 |
| 动态补位 | 玩家长时间盯着 A 路时，AI 优先加强 B / C 路 |
| 目标选择 | 优先打自己扇区内最近的敌人；扇区无敌人时支援邻近扇区 |
| 换弹 | 弹匣打空即换，换弹期间蹲下 |
| 呼救 | 发现某路线敌人密集时喊话提示（如「西侧上来了！」）并在小地图标记 |

**设计意图**：AI 队友的喊话与标记是**给玩家的信息补偿** —— 玩家看不住三条路，但队友会告诉他哪条路吃紧。这把「兼顾多路」的操作压力转化为「听信息做决策」的策略压力，更适合 9–15 岁的目标用户。

### 2.6 胜负判定

| 结果 | 条件 |
|---|---|
| 胜利 | 5:00 结束时，**玩家本人**仍存活 |
| 失败 | 玩家在 5:00 前阵亡 |
| 提前结束 | 5 名成员（含 AI 队友）全部阵亡 → 立即结算失败 |
| MVP | 见 2.7 |

> **注意**：胜负只看玩家本人是否存活。AI 队友全部阵亡但玩家还活着 —— **依然是胜利**，这符合「五壮士坚守到最后」的叙事。

### 2.7 MVP 评选

**MVP 只在真人玩家中产生，AI 队友不参评。**

| 情况 | MVP 处理 |
|---|---|
| 单人模式 | 玩家存活即为 MVP，展示其歼敌数与 AI 队友对比 |
| 多人模式 | 存活玩家中歼敌数最高者 |

平局判据依次为：歼敌数 → 重机枪歼敌数 → 存活时长 → 命中率。

### 2.8 玩家阵亡规则

- 玩家阵亡后**不复活**，转为观战模式（可切换视角观看队友与 AI 队友）
- 阵亡玩家的歼敌数计入战报，但**不参与 MVP 评选**
- 阵亡不影响其他成员继续战斗，战斗持续到 5:00 或全员阵亡

## 3. 技术选型（已锁定，不得擅自更换）

### 3.1 整体架构

```
┌─────────────────────────────────────────────┐
│  客户端 Cocos Creator 3.8 (Web-Mobile 构建)   │
│  职责：渲染表现 / 输入采集 / 音效 / UI        │
│  ⚠️ 不做任何胜负与伤害判定                    │
└──────────────────┬──────────────────────────┘
                   │ WebSocket (二进制/JSON)
                   │ 20 Hz 状态同步
┌──────────────────┴──────────────────────────┐
│  权威服务器 Node.js + TypeScript              │
│  职责：房间管理 / 敌人AI / 伤害判定 /          │
│        命中裁决 / 补给投放 / 战报结算          │
│  运行环境：Debian 13 工作站 (192.168.1.80)    │
└─────────────────────────────────────────────┘
```

### 3.2 技术栈明细

| 层 | 技术 | 版本 | 说明 |
|---|---|---|---|
| 客户端引擎 | Cocos Creator | 3.8.x LTS | 构建目标 Web-Mobile |
| 客户端语言 | TypeScript | 5.x | 严格模式开启 |
| 服务端运行时 | Node.js | 22.x LTS | 与工作站现有 Node 版本对齐 |
| 服务端语言 | TypeScript | 5.x | 与客户端共享 `shared/` 协议定义 |
| 网络协议 | WebSocket (`ws` 库) | - | 不用 socket.io，避免额外开销 |
| 房间状态 | 内存 Map | - | v1.0 不引入 Redis |
| 战报持久化 | SQLite | - | 单文件，便于备份与教学演示 |
| 构建部署 | Cocos CLI + PM2 + Nginx | - | 见第 10 章 |

### 3.3 画面形态：2.5D（3D 场景 + 2D 角色）

| 元素 | 实现方式 | 理由 |
|---|---|---|
| 山地地形 | 3D 低模网格（代码生成高度图或简化 mesh） | 表现「居高临下」的高低差与遮挡关系 |
| 敌我角色 | 2D Billboard 面片（始终朝向摄像机） | 复用现有 1024 概念图产出的立绘，成本可控 |
| 武器（第一人称手部） | 2D 贴图叠加在屏幕层 | 直接使用 `武器素材/*/right.png` |
| 特效（枪口焰/弹着尘） | 3D 粒子系统 | Cocos 内置粒子即可 |
| 摄像机 | 第一人称，可俯仰 ±60°，水平 360° | 玩家固定在阵地区域，仅小范围移动 |

**为何是 2.5D 而不是纯 3D**：现有全部素材（军服 T-pose 图、武器侧视图）都是 **2D 参考图，无任何模型文件**。纯 3D 需要重新建模、UV、贴图、绑骨、动画，美术成本翻数倍且不可控；2.5D 让 3D 只承担「地形高低差」这一必须由 3D 解决的问题，其余全部走 2D 管线。

### 3.4 云端开发落地方式

| 环节 | 位置 | 说明 |
|---|---|---|
| 服务端全部代码 | Debian 工作站，Codex 直接改 | 纯 TypeScript，无 GUI 依赖 |
| 客户端逻辑代码 | Debian 工作站，Codex 直接改 | `assets/scripts/` 下的 `.ts` 文件 |
| 场景 / 预制体 | **尽量用代码动态生成** | 减少对 Creator 编辑器的依赖 |
| 构建打包 | Debian 上跑 Cocos CLI 无头构建 | `CocosCreator --build "platform=web-mobile"` |
| 必须开编辑器的操作 | watson 本地 Mac 处理 | 仅限场景美术微调，属于少量兜底 |

**关键约束（给 Codex）**：场景结构请用 **代码构建**（在 `GameScene.ts` 的 `onLoad` 中动态 `instantiate` 节点），而不是依赖 `.scene` 文件里手工摆放的节点。`.scene` 文件只保留一个空根节点 + 摄像机 + 一个挂载入口脚本的节点。这样云端改代码即可改场景，无需 GUI。

## 4. 关卡与场景设计

### 4.1 战场布局

```
                    ▲ 北（山顶阵地 — 玩家区域）
        ┌───────────────────────────────┐
        │  [MG1]    棋盘陀       [MG2]   │   高程 +40m
        │      P1  P2  P3  P4  P5       │   5个席位（真人+AI队友）
        │   ▓▓ 石垒掩体 ▓▓▓ 石垒 ▓▓▓     │
        └───┬───────────┬───────────┬───┘
            │           │           │
         [路线A]     [路线B]     [路线C]      高程 +20m 中段坡地
         正面陡坡     侧翼缓坡     背面绕行
          短·险       中·开阔      长·隐蔽
            │           │           │
        ┌───┴───────────┴───────────┴───┐
        │        日军集结区（刷新点）      │   高程 0m
        └───────────────────────────────┘
                    ▼ 南（山脚）
```

### 4.2 三条进攻路线

| 路线 | 长度 | 掩体密度 | 到达时间 | 敌军配比 | 战术含义 |
|---|---|---|---|---|---|
| A 正面陡坡 | 短（约 60m） | 低 | ~18 秒 | 50% | 主攻，暴露度高，易被压制 |
| B 侧翼缓坡 | 中（约 90m） | 中 | ~28 秒 | 30% | 迂回，轻机枪火力组多走此路 |
| C 背面绕行 | 长（约 130m） | 高 | ~40 秒 | 20% | 偷袭，容易被玩家忽略，威胁最大 |

**设计意图**：单人无法同时看住三条路，必须靠 5 人编成（真人 + AI 队友）才能形成完整防线。单人模式下，AI 队友会分守玩家没盯住的路线并喊话提示。

**AI 队友默认布防**：单人模式下，玩家默认在 A 路（正面），4 名 AI 队友按 A×1 / B×2 / C×1 分配；玩家换位时 AI 动态补位。

### 4.3 关键场景元素

| 元素 | 数量 | 说明 |
|---|---|---|
| 出生点 | 5 | 沿山顶横向排布，间距 8m；真人优先占位，余位给 AI 队友 |
| 重机枪位（MG） | 2 | 固定架设点，见 5.4 |
| 石垒掩体 | 6 | 玩家可蹲下减少受击面积 |
| 弹药补充箱 | 3 | 固定位置，可无限补弹（有冷却） |
| 补给空投点 | 5 | 随机血包落点，见 5.5 |
| 敌军刷新点 | 3 | 对应三条路线的起点，玩家视野外 |

### 4.4 玩家移动范围

玩家**不能下山**。活动区域为山顶阵地矩形区（约 60m × 20m），越界时给出提示「坚守阵地！」并被软墙挡回。

**理由**：这是固守玩法，不是开放战场；限制范围可大幅降低地形制作成本与网络同步压力。

## 5. 数值设计（唯一数据源）

> **给 Codex**：本章所有数值必须落到 `shared/config/*.json`，服务端与客户端共同读取。禁止在业务代码中硬编码任何数值。

### 5.1 玩家属性

| 属性 | 数值 | 备注 |
|---|---|---|
| 最大生命值 | 100 | |
| 初始生命值 | 100 | |
| 自然回复 | 无 | 只能靠血包 |
| 移动速度 | 4.0 m/s | 山顶阵地内 |
| 蹲下速度 | 1.8 m/s | 受击面积减少 40% |
| 初始血包 | 2 个 | 见 5.5 |

### 5.2 玩家武器（中国军队）

| 武器 | 素材目录 | 伤害 | 射速 | 弹匣 | 备弹 | 换弹 | 有效射程 | 精度 |
|---|---|---|---|---|---|---|---|---|
| 中正式步枪 | `武器素材/liaoshi13` | 55 | 0.9 发/秒 | 5 | 60 | 3.2s | 200m | 高（单发栓动） |
| 李恩菲尔德 No.4 | `武器素材/lee-enfield-no4` | 50 | 1.4 发/秒 | 10 | 60 | 3.8s | 180m | 高 |
| ZB26 轻机枪 | `武器素材/zb26` | 32 | 8 发/秒 | 20 | 120 | 4.0s | 150m | 中（连发扩散） |
| 布伦轻机枪 | `武器素材/bren` | 34 | 8.3 发/秒 | 30 | 120 | 4.2s | 160m | 中 |

### 5.3 敌方单位（日军 AI）

| 单位 | 素材 | HP | 武器 | 伤害 | 移动速度 | 占比 | AI 行为 |
|---|---|---|---|---|---|---|---|
| 步枪兵 | `japanese-army-soldier` | 100 | 三八式 | 18 | 3.2 m/s | 70% | 交替跃进，利用掩体 |
| 轻机枪手 | `japanese-army-soldier` | 120 | 轻机枪 | 12×连发 | 2.4 m/s | 20% | 寻找位置架枪压制 |
| 突击兵 | `japanese-army-soldier` | 80 | 三八式 | 15 | 4.5 m/s | 10% | 高速冲锋，不惜代价 |

**敌方通用规则**：
- **无血包、无治疗、无复活**，HP 归零即永久移除
- 命中玩家有 0.35 秒预警（枪口焰可见），给玩家反应窗口
- 距离衰减：>120m 伤害 ×0.6，>180m 不开火

**四波难度递增**：

| 波次 | 命中精度 | 兵种构成 | 说明 |
|---|---|---|---|
| 第一波 | 55% | 步枪兵 90% / 轻机枪 10% | 教学波，容错高 |
| 第二波 | 65% | 步枪兵 70% / 轻机枪 20% / 突击兵 10% | 标准编成 |
| 第三波 | 72% | 步枪兵 65% / 轻机枪 20% / 突击兵 15% | 三路齐攻 |
| 第四波 | 80% | 步枪兵 55% / 轻机枪 20% / 突击兵 25% | 总攻，突击兵大幅增加 |

### 5.4 重机枪（九二式）

| 属性 | 数值 |
|---|---|
| 素材 | `武器素材/type92-hmg` |
| 数量 | 2 个固定枪位（MG1 / MG2） |
| 伤害 | 45 / 发 |
| 射速 | 7.5 发/秒 |
| 弹链 | 250 发 |
| 过热 | 连续射击 6 秒过热，强制冷却 4 秒 |
| 补弹 | 弹链打空后 8 秒重新装填 |
| 射界 | 水平 ±70°（受枪架限制），俯仰 -50°~+15° |
| 使用限制 | 使用时玩家移动锁定，受击面积 +30%（高风险高回报） |
| 占用 | 同一枪位同时仅 1 名玩家可用 |
| AI 队友 | **不可使用**，重机枪是真人玩家专属资源 |

**设计意图**：重机枪是清理密集冲锋的核心手段，但会让使用者变成靶子 → 需要队友掩护，强化协作。单人模式下 AI 队友不占枪位，玩家随时可用。

### 5.5 血包与补给

| 类型 | 回复量 | 数量 | 说明 |
|---|---|---|---|
| 随身血包（玩家） | 40 HP | 每人初始 2 个 | 使用耗时 2.5 秒，期间不能开火 |
| 随身血包（AI 队友） | 40 HP | 每个 1 个 | HP < 30% 时自动使用 |
| 空投血包 | 50 HP | 随机 | 落地即拾取生效，**仅真人玩家可拾取** |

**空投规则**：
- 触发时机：每波间歇期 + 战斗中每 45 秒一次
- 落点：5 个预设补给点中随机选 1–2 个
- 存在时间：25 秒后消失
- 拾取：先到先得，真人玩家间共享；**AI 队友不参与抢夺**
- 空投时全场提示「补给空投！」+ 地图标记

### 5.6 AI 队友数值

| 属性 | 数值 | 说明 |
|---|---|---|
| 数量 | 5 − 真人数 | 单人模式为 4 |
| 生命值 | 100 | 与玩家一致 |
| 武器 | 中正式步枪 | 固定，不切换、不拾取 |
| 伤害 | 55 | 与玩家同枪同伤害 |
| 射速 | 0.7 发/秒 | 玩家为 0.9 |
| 命中率 | 55% | 距离 >120m 时降至 35% |
| 反应延迟 | 0.6 秒 | 发现敌人到开火的延迟 |
| 随身血包 | 1 个 | 自动使用 |
| 重机枪 | 不可用 | 保留给真人 |
| 空投拾取 | 不拾取 | 保留给真人 |
| 阵亡 | 不复活 | 与玩家一致 |

**预期歼敌占比**：4 名 AI 队友合计承担全场约 40%，玩家需完成约 60%。**Codex 在 M2 阶段需实测校准此比例**，若 AI 队友包办超过 50%，下调命中率或射速。

### 5.7 时间轴

| 时间 | 事件 | 敌军 |
|---|---|---|
| 0:00 – 0:10 | 部署期，选武器、选位置，敌人不刷新 | — |
| 0:10 – 1:15 | 第一波（每 15 秒 10 人） | 30 |
| 1:15 – 1:27 | 间歇 + 空投 | — |
| 1:27 – 2:32 | 第二波（每 12 秒 12 人） | 50 |
| 2:32 – 2:44 | 间歇 + 空投 | — |
| 2:44 – 3:52 | 第三波（每 12 秒 15 人） | 60 |
| 3:52 – 4:04 | 间歇 + 空投 | — |

| 5:00 | 结算 | 合计 200 |

> **给 Codex**：时间轴的严格性低于总量。若因同屏上限导致投放延后，**以「打满 200 人」为准，允许第四波压到 5:00 仍有残余敌人**，结算时按实际歼敌数计分。

### 6.2 ⚠️ 核心风险提示（Codex 必读）

**现有素材全部是「概念参考图」，不是可直接使用的游戏资源。**

具体问题：
1. 军服图是 **T-pose 全身写实渲染图**，带灰色背景，**没有抠图、没有动作序列**
2. 武器图分辨率过高（最大 2277px），直接入包会让 Web 首屏加载爆炸
3. 中文目录名 `手榴弹/` 在部分构建管线中可能出问题

**因此必须先执行 6.3 的二次加工流程，加工产物放在 `assets/resources/` 下，原始素材目录保持只读不动。**

### 6.3 素材二次加工流程

```
原始素材（只读）              加工产物（游戏使用）

武器素材/*/right.png    →    assets/resources/weapons/liaoshi13_fp.png
```

| 用途 | 目标尺寸 | 格式 | 说明 |
|---|---|---|---|
| 角色 Billboard | 512×512 | PNG 透明通道 | 需抠除灰色背景 |

**目录命名规范**：加工产物一律使用**英文目录名**，`手榴弹/` → `grenade/`。

### 6.4 角色动作帧需求

现有素材只有静态 T-pose，需要生成以下动作状态。**v1.0 采用简化方案**：

| 状态 | 实现方式 | 帧数 |
|---|---|---|
| 站立/待机 | 静态图 + 轻微上下浮动（代码补间） | 1 |
| 奔跑 | 静态图 + 左右轻微摇摆 + 位移（代码补间） | 1 |
| 中弹 | 静态图 + 红色闪烁 + 后仰旋转 | 1 |

**设计取舍**：不做逐帧动画。用**代码补间（tween）+ 图片变换**模拟动作，成本极低且在 2.5D Billboard 视角下观感可接受。若后续需要提升品质，再补逐帧序列图，接口预留 `AnimState` 枚举。

## 7. 联网设计（权威服务器）

### 7.1 核心原则

**客户端只负责「看」和「说」，服务器负责「算」和「判」。**

| 职责 | 归属 |
|---|---|
| 玩家输入采集、画面渲染、音效 | 客户端 |
| 敌人 AI 决策与移动 | 服务器 |
| **AI 队友决策与移动** | 服务器 |
| 伤害计算、命中判定 | 服务器 |
| 血包生成与拾取仲裁 | 服务器 |
| 胜负判定、MVP 评选 | 服务器 |
| 战报持久化 | 服务器 |

**反作弊底线**：客户端上报的是「我在这个方向开了一枪」，**不是**「我打死了谁」。所有击杀由服务器裁决。

### 7.2 单人模式也走服务器（重要架构决策）

**单人模式不做本地化特例，同样连服务器、同样走完整协议。**

| 方案 | 评价 |
|---|---|
| 单人跑本地逻辑，联机跑服务器 | ❌ 要写两套战斗逻辑，数值与行为必然漂移，后期联机等于重做 |
| **单人也连服务器，房间人数为 1**（采纳） | ✅ 一套逻辑通吃，M2 做完的单人战斗到 M3 直接变成联机 |

**收益**：AI 队友和敌人 AI 都跑在服务端，单人与联机共用同一份 `ai/` 代码。**M2 阶段做的所有战斗调优，在 M3 联机时零成本继承。**

**代价**：单人模式也依赖服务器可用性，不能离线玩。考虑到本项目定位为课程演示与在线作品，这个代价可以接受。

### 7.3 房间模型

| 属性 | 规则 |
|---|---|
| 席位总数 | **恒定 5 席**（对应五壮士） |
| 真人容量 | 1–5 人 |
| AI 队友 | 自动补齐至 5 席（单人时 4 个） |
| 阵营 | 全部为中国军队，**无阵营选择入口** |
| 单人开局 | 点「单人作战」直接开，无需等待 |
| 联机匹配 | 房间码加入 + 快速匹配 |
| 联机开局 | 房主点击开始（不必满员，空位补 AI） |
| 中途加入 | v1.0 不允许（开局后锁定） |
| 掉线处理 | 保留角色 60 秒等待重连；超时**转为 AI 队友接管**，对局继续 |
| 房主掉线 | 服务器托管，不影响对局 |

> **掉线转 AI 接管**是 AI 队友系统的额外收益：因为已经有了队友 AI，掉线玩家可以无缝转交给 AI，不必让队友陷入减员劣势。

### 7.4 同步策略

| 项 | 方案 |
|---|---|
| 状态同步频率 | 20 Hz（每 50ms 一个快照） |
| 客户端预测 | 玩家自身移动本地预测 + 服务器校正 |
| 敌人表现 | 客户端插值平滑（缓冲 100ms） |
| 射击 | 客户端立即播放特效（表现），服务器回包确认命中结果 |
| 带宽控制 | 只同步玩家视野内的敌人；快照差量压缩 |

**关键实现要求**：40 个敌人 × 20Hz 全量同步会撑爆带宽，必须做**视野裁剪 + 差量更新**。位置用 int16 量化，不传 float。

### 7.5 协议定义

**客户端 → 服务器**

| 消息 | 字段 | 说明 |
|---|---|---|
| `start_solo` | playerName | 开始单人作战（服务端自动补 4 名 AI 队友） |
| `join_room` | roomCode, playerName | 加入联机房间 |
| `player_ready` | - | 准备就绪 |
| `input_state` | moveDir, aimYaw, aimPitch, isCrouch | 20Hz 上报 |
| `fire` | weaponId, originPos, dirVec, clientTick | 开火请求 |
| `reload` | weaponId | 换弹 |
| `use_medkit` | - | 使用随身血包 |
| `pickup` | itemId | 拾取（血包/弹药/武器） |
| `mount_mg` | mgId | 上重机枪 |
| `unmount_mg` | - | 下重机枪 |
| `throw_grenade` | dirVec, force | 投掷手榴弹 |

**服务器 → 客户端**

| 消息 | 字段 | 说明 |
|---|---|---|
| `room_state` | seats[], status | 5 个席位状态（含 AI 队友标记） |
| `match_start` | timestamp, config, teammates[] | 开局，含 AI 队友名单 |
| `world_snapshot` | tick, allies[], enemies[], items[] | 20Hz 世界快照 |
| `fire_result` | hit, targetId, damage, isKill, hitPart | 开火裁决 |
| `ally_damaged` | allyId, hp, fromDir | 友方受伤（含 AI 队友） |
| `ally_died` | allyId, isBot, killerType | 友方阵亡（含 AI 队友） |
| `enemy_died` | enemyId, killerId, killerIsBot | 敌人被消灭，标记是否 AI 队友击杀 |
| `ally_callout` | allyId, routeId, text | **AI 队友喊话提示**（如「西侧上来了」） |
| `wave_start` | waveIndex, enemyCount, totalWaves | 波次开始（共 4 波） |
| `supply_drop` | dropId, position | 空投 |
| `match_end` | result, scoreboard, mvpPlayerId | 结算 |

> **给 Codex**：`world_snapshot` 中 AI 队友与真人玩家统一放在 `allies[]` 数组，用 `isBot` 字段区分。客户端渲染时**完全一致**（同样的角色素材、同样的动画），只在 HUD 队友列表上加一个小标识。这样单人与联机的渲染代码完全复用。

### 7.6 计分与 MVP

服务端维护每位玩家的：

```
kills          总歼敌数
mgKills        重机枪歼敌数（MVP 第一优先级平局判据）
headshots      爆头数
damageDealt    总伤害
survivalTime   存活时长
accuracy       命中率
```

**MVP 算法**：
1. 筛选**存活的真人玩家**（阵亡者与 AI 队友均不参评）
2. 按 `kills` 降序
3. 平局 → 比 `mgKills`
4. 再平局 → 比 `survivalTime`
5. 仍平局 → 比 `accuracy`

**AI 队友计分**：AI 队友的歼敌数**单独统计并在战报中展示**，但不参与 MVP 竞争。战报中的呈现方式：

```
战报 — 坚守成功

  马宝玉（你）      歼敌 48   命中率 62%   ★ MVP
  葛振林（AI）      歼敌 21
  宋学义（AI）      歼敌 18
  胡德林（AI）      歼敌 15
  胡福才（AI）      歼敌 12   已阵亡

  全队歼敌 114 / 200
```

**设计意图**：把玩家成绩与 AI 队友并列展示，玩家能直观看到自己扛了多少 —— 这是单人模式的核心成就反馈。若玩家歼敌数低于 AI 队友，说明数值需要下调（见 5.6 校准要求）。

## 10. 部署方案

### 10.1 职责边界（重要）

**Codex 的交付边界：在 Debian 工作站上把服务部署好、跑起来、本机可访问即可。**

| 事项 | 负责方 |
|---|---|
| 服务端部署、PM2 常驻、开机自启 | **Codex** |
| 客户端构建产物落到指定目录 | **Codex** |
| 本机 Nginx 站点配置（监听本地端口） | **Codex** |
| 域名解析、对外 Nginx 反向代理 | **watson** |
| Tailscale 内网转发链路 | **watson** |
| 证书 / HTTPS | **watson** |

> **Codex 不需要配置 frpc，也不需要处理域名和外网暴露。** 只要保证服务在 Debian 上稳定监听指定端口，watson 会在自己的转发层用域名 + Nginx 经 Tailscale 内网接入。

### 10.2 环境

| 角色 | 机器 | 说明 |
|---|---|---|
| 开发 / 构建 | Debian 13 工作站 | Codex 主要工作区 |
| 服务端运行 | 同上 | PM2 常驻，开机自启 |
| 静态资源 | 同上 Nginx | 托管 `build/web-mobile` |
| 内网访问地址 | 局域网 192.168.1.80 / Tailscale 100.126.150.80 | 两个地址都应可访问 |
| 对外入口 | watson 自行配置域名 + Nginx 转发 | 不在本次交付范围 |

### 10.3 端口规划

| 端口 | 用途 | 监听地址 |
|---|---|---|
| 8080 | Nginx 静态站点（游戏客户端） | `0.0.0.0`（需 Tailscale 可达） |
| 8081 | WebSocket 游戏服务 | `0.0.0.0`（需 Tailscale 可达） |
| 5212 | SSH（已有） | — |
| 5900 | VNC（已有） | — |

**监听地址说明**：因为要经 Tailscale 内网转发访问，服务需监听 `0.0.0.0` 而非仅 `127.0.0.1`，否则 Tailscale 接口无法访问。**这台机器不直接暴露公网，由 watson 的转发层控制入口，因此监听 0.0.0.0 是安全的。**

### 10.4 WebSocket 地址配置

客户端连接的 WS 地址**必须可配置**，不能硬编码。

```
client/assets/resources/config/server.json
{
  "wsUrl": "",        // 留空则自动用当前页面 host，端口 8081
  "wsPath": "/ws"
}
```

**默认行为**：客户端从当前访问的域名推导 WS 地址。这样 watson 换域名或改转发时，**不需要重新构建客户端**。

> **给 Codex**：建议 Nginx 同时反代 `/ws` 到 8081，让客户端与 WS 走同一端口同源访问，可彻底避免跨域与混合内容问题。这样 watson 的转发层只需转发一个端口。

### 10.5 部署命令

```bash
# 服务端
cd server && npm ci && npm run build
pm2 start dist/index.js --name langyashan-server
pm2 save && pm2 startup      # 开机自启

# 客户端无头构建
CocosCreator --project ./client --build "platform=web-mobile;debug=false"

# 构建产物同步到 Nginx 站点目录
rsync -a --delete client/build/web-mobile/ /var/www/langyashan/
```

**交付验证（Codex 必须自测通过）**：
```bash
curl -I http://127.0.0.1:8080              # 静态站点 200
curl -I http://100.126.150.80:8080         # Tailscale 地址可达
# WebSocket 连通性自测脚本
node tools/check-ws.js ws://127.0.0.1:8081/ws
```

### 10.6 性能目标

| 指标 | 目标 |
|---|---|
| 首屏加载 | < 8 秒（4G 网络） |
| 资源总体积 | < 25 MB |
| 战斗帧率 | PC ≥ 50 FPS，移动端 ≥ 30 FPS |
| 网络延迟容忍 | 150ms 内体验无明显异常（Tailscale 转发会增加延迟，需实测） |
| 服务器单局 CPU | < 20%（单核，含 4 个 AI 队友 + 40 个敌人） |
| 并发对局数 | ≥ 5 局同时进行不掉帧 |

## 11. 开发排期（建议 Codex 按此顺序推进）

**v1.0 主线是单人模式。** 联机在架构上已预留（单人也走服务器），但作为后置里程碑。

| 阶段 | 内容 | 产出判据 |
|---|---|---|
| **M0 骨架** | 工程初始化、`shared/protocol.ts`、配置 JSON、WS 连通、部署跑通 | 浏览器能连上服务器并收到心跳 |
| **M1 战斗核心** | 地形生成、玩家移动射击、1 种敌人、伤害判定、命中反馈 | 能打死一个敌人，手感成立 |
| **M2 AI 队友** | 4 名 AI 队友、布防补位、喊话提示、队友 HUD | 单人开局能看到 4 名队友一起作战 |
| **M3 完整单局** | 四波次、三路线、三种敌人、重机枪、血包、5 分钟计时、结算 | **单人能完整打完一局并看到战报** |
| **M4 美术接入** | 素材加工管线、角色 Billboard、武器立绘、UI、音效 | 画面达到可展示水平 |
| **M5 联机** | 房间、匹配、多人同步、掉线转 AI 接管 | 2 人以上同房对战，成绩正确 |
| **M6 打磨上线** | 性能优化、移动端适配、部署固化 | 通过第 12 章全部验收项 |

**关键节点**：
- **M3 完成必须给 watson 试玩**，确认手感与难度曲线后再进 M4。这是整个项目最重要的验证点 —— 如果单人不好玩，加美术和联机都救不回来。
- **M2 完成时需实测 AI 队友歼敌占比**，超过 50% 就下调其命中率（见 5.6）。
- M4 之前用色块占位即可，不要因为等美术资源阻塞玩法开发。

## 12. 验收清单

### 12.1 玩法验收

- [ ] 单局固定 5 分钟，计时准确
- [ ] **四波敌人按 30 / 50 / 60 / 60 生成，总数恰好 200**
- [ ] 各波按小队滚动投放，同屏存活不超过 40

## 13. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **素材不可直接用** | 高 | 第 6 章已明确二次加工流程；M4 前先跑通 1 个角色 1 把枪验证管线 |

| 服务端 AI 计算压力 | 中 | 4 个队友 + 40 敌人 = 44 个 AI 实体。用预设路径点 + 分帧计算，不做实时寻路 |
| 云端无 GUI 难改场景 | 中 | 场景由代码生成，`.scene` 保持极简；必要时 watson 本地兜底 |
| Tailscale 转发延迟 | 中 | 客户端预测 + 100ms 插值缓冲；M0 阶段即实测 Tailscale 链路延迟 |
| 带宽超标 | 中 | 差量同步 + int16 量化 + 视野裁剪 |
| 适龄合规争议 | 高 | 无血腥表现；发布前由 watson 审看 |
