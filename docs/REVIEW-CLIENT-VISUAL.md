## 0. 一句话结论

当前客户端**工程质量不差、但呈现层是「调试面板」而不是「游戏画面」**。
真正的风险不在 M4 换素材，而在于 HUD 的信息架构、渲染管线和画布适配这三处结构性欠账 —— 这些东西**不会因为把色块换成立绘而自动变好**，反而会在 M4 之后变成难改的技术债。

**优先级最高的三件事**（建议在 M3 收尾前处理，成本低、收益大）：

1. **P0-1 摄像机无环境光照 + `builtin-unlit` 材质** → 无论换什么素材画面都是「平的」
2. **P0-2 HUD 大量暴露调试文案与延迟数字** → 直接毁掉沉浸感，家长第一眼看到的就是「这是个半成品」
3. **P0-3 `ResolutionPolicy.SHOW_ALL` + 绝对像素定位 HUD** → 非 16:9 屏幕上留黑边、元素错位

## 1. P0 级：会直接决定「丑不丑」的结构性问题

### P0-1 渲染管线：全场 `builtin-unlit`，画面必然是平的

**现状**

- `enemy-renderer.ts:190-198`、`ally-renderer.ts:121-129` 全部使用 `builtin-unlit` + 纯色
- `first-person-controller.ts:62-63` 摄像机 `clearFlags = SOLID_COLOR`，纯色天空 `#53687A`
- `Boot.scene` 里 `AmbientInfo` / `SkyboxInfo` / `ShadowsInfo` 都是默认值，代码里没有任何 `DirectionalLight`
- 场景里没有任何光源节点

**问题**

`unlit` 材质不吃光照，物体不管朝向如何都是同一个颜色。结果就是：

- 地形没有明暗，「居高临下」的高低差感受不到（PRD 3.3 选 2.5D 的**唯一理由**就是表现高低差）
- 敌人色块和地面色块在视觉上是「贴在一起的两块颜色」，没有立体分离
- M4 把 Billboard 立绘贴上去后，角色和地形依然是两个割裂的图层，不会更好

**⚠️ 概念澄清（重要，避免误解为"要在山上装灯"）**

这里说的「光照」是**渲染意义上的光源**，不是场景里的灯具。两者完全不同：

| 概念 | 含义 | 与史实的关系 |
|---|---|---|
| 渲染光源（`DirectionalLight` 等） | 3D 引擎的数学参数，决定物体每个面的明暗 | **无关**。任何能看清的 3D 场景都必须有，正午荒野也一样 |
| 场景灯具（电灯 / 煤油灯 / 火把） | 世界里真实存在的可见物件 | 有关，需要考据 |

**缺渲染光源 ≠ 画面很暗**，而是所有物体每一面都同色，像一堆剪纸贴在屏幕上——石垒看不出凹凸，山坡看不出坡度。1941 年狼牙山上有没有电，与是否需要 `DirectionalLight` 没有任何关系。

**史实光照设定（已考据，可直接照做）**

来源：中国军网《狼牙山五壮士：五人三烈士，战史壮高风》、人民政协网《狼牙山五壮士气吞山河》、央视网葛振林口述回忆。

| 时间 | 史实事件 | 对应本作 | 光照 |
|---|---|---|---|
| 1941-09-24 深夜 | 七连主力撤离；六班五人**借着月光**将团部留下的几箱手榴弹捆成束，从山脚埋到半山腰 | **部署期 0:00–0:10** | 冷蓝月光为主光，地平线可点缀煤油灯暖光 |
| 09-25 清晨 6:00 | 500 余日伪军发起进攻，8:30 接火 | 第一波（0:10 起） | 低角度晨光，长投影 |
| 至「太阳偏西」 | 打退 4 次冲锋后撤向棋盘陀顶峰 | 第三 / 四波 | 太阳升高转午后斜光 |

**结论：5 分钟战斗单局历史上对应 25 日白天（清晨到午后），主光源是太阳，不需要任何人造照明。**
原文表述「黄昏侧光」有误，PRD 8.5 的「黄昏/阴天」建议按史实修正为**清晨转午后**。

**建议**

| 动作 | 说明 |
|---|---|
| 加一盏 `DirectionalLight` 作为太阳 | 代码创建。低角度晨光起手，色温偏冷白；随波次推进可缓慢抬高角度、转暖，做出时间流逝感 |
| 加一盏低强度环境光 / 半球光 | 避免背光面纯黑，山地背阴处仍需可辨敌人轮廓（**玩法需求，不只是美观**） |
| 地形/掩体改 `builtin-standard` 或 `builtin-toon` | 角色 Billboard 保留 unlit（立绘自带光影），场景物件吃光照 |
| 启用 `SkyboxInfo` 或做渐变天空 | 纯色 `#53687A` 最廉价；换成两段渐变（天顶冷、地平线暖）成本极低、观感提升明显 |
| 开启 `FogInfo` 线性雾 | 晨雾符合山地清晨史实；同时让远处敌人淡入背景，缓解 `cameraFarM=200` 的远裁切突兀感 |

**成本评估**：约 60–100 行代码 + 6 个配置项，不影响任何协议和服务端逻辑。**建议 M3 就做，不要等 M4**，因为 M4 调素材时需要真实光照环境才能判断立绘明暗对不对。

### P0-1b 部署期「月夜埋雷」过场（史实彩蛋，强烈建议做）

**依据**

葛振林生前口述（央视网）：「连队主力撤离后，我们趁着月色，把团部留下的几箱手榴弹，捆作一束一束，当地雷从山脚一直埋到半山腰。」
人民政协网记载一致：五人「借着月光」分束扎捆手榴弹后，隐蔽于「阎王鼻子」与「小鬼脸儿」两处待敌。

**现状**

PRD 5.7 定义了 `0:00–0:10` 部署期，PRD 8.5 要求「开局前 10 秒部署期展示历史背景字幕」，但目前**这 10 秒是空的**，客户端没有任何对应实现。

**建议**

把部署期做成 **24 日深夜 → 25 日清晨** 的光照转场：

1. 开局：冷蓝月光（低强度方向光 + 偏蓝环境光），场景近乎剪影
2. 地平线方向放 1–2 个暖色点光源，暗示山下宿营的煤油灯/马灯 —— **这是 watson 提出的点，史实上成立且氛围加分**
3. 叠加历史背景字幕（可复用 PRD 8.5 已规划的文案）
4. 第 8–10 秒，方向光角度抬升、色温转暖、强度拉满，天空由深蓝转晨白，无缝切入第一波

**为什么值得做**

- 一次光照转换就把「深夜准备 → 清晨接战」的时间跨度讲清楚，比单纯放字幕高出一个层级
- 教学价值：学员会记住「他们是提前一晚埋好雷的」，而不只是「打枪」——符合 PRD 1.2「课程教学案例」定位
- 技术上是**同一套光照系统的参数补间**，做完 P0-1 后增量成本极低（约 30 行 + 一组配置）

**注意**：手榴弹埋雷仅作为过场叙事，**不要引入实际的地雷玩法**——PRD 未定义，属于自行发挥，违反铁律 1。

### P0-2 HUD 是调试面板，不是游戏界面

**现状**（`ui/m1-hud.ts`）

屏幕上同时常驻这些文本：

| 位置 | 文案 | 问题 |
|---|---|---|
| 顶部标题 | `M2 五人防线 · 服务器权威 AI` | 里程碑代号出现在玩家眼前 |
| 顶部第二行 | `已连接，延迟 12 ms` | 调试信息常驻 |
| 中部 | `等待权威快照…` / `已开火，等待服务器裁决…` | 内部架构术语泄漏给玩家 |
| 命中反馈 | `命中 55 · 裁决 7 ms` | 玩家不需要知道「裁决」和毫秒 |
| 敌人计数 | `敌人 15 · 所有伤害等待服务器裁决` | 同上 |
| 底部帮助 | `点击画面锁定鼠标 \| WASD 移动 \| ...` | 一行长文本永久占据底部 |

**挑剔用户视角**：一个 12 岁孩子打开页面，看到的第一屏是「M2 五人防线 · 服务器权威 AI」和「等待权威快照…」。这不是游戏，这是开发者工具。家长看到会直接判定「没做完」。

**建议**

1. **分离玩家文案与调试文案**
   - 玩家可见文案单独抽一份 `presentation-strings.json`（也便于教学时讲「文案配置化」）
   - 调试信息移到 `?debug=1` 查询参数开启的独立层，默认隐藏
   - 现有的 `window.__LANGYASHAN_M1__` 和 `data-langyashan-m1` 属性是很好的自动化测试通道，**保留**，但不要再往可见 HUD 上打调试字
2. **文案改写**（示例，非强制）
   - `已开火，等待服务器裁决…` → 不显示任何文字，靠枪口焰和后坐表现
   - `命中 55 · 裁决 7 ms` → 只飘 `55` 伤害数字
   - `敌人 15 · 所有伤害等待服务器裁决` → `剩余敌军 15`
   - `M2 五人防线 · 服务器权威 AI` → 战斗中不需要标题，删掉；标题放启动页
3. **帮助文案改成首次进入的引导浮层**，3 秒后淡出，或按 `Tab` 唤出（PRD 8.3 已规划 Tab 为记分板，可考虑 `H` 或 `?`）
   - PRD M6 才要求新手引导，但**把常驻帮助行换成一次性浮层是 M3 就能顺手做掉的**

**注意**：`m1-hud.ts:32` 有一处错别字 —— `invalid_direction: '矄准方向无效'`，应为「瞄准」。这个字会真的显示给玩家。

### P0-3 画布适配：`SHOW_ALL` + 绝对像素定位

**现状**

- `m1-game.ts:86-90` 使用 `ResolutionPolicy.SHOW_ALL`，设计分辨率 1280×720
- `Boot.scene` 的 Canvas `_contentSize` 是 960×640，与代码里设的 1280×720 **不一致**
- 所有 HUD 元素用 `presentation.json` 里的绝对像素坐标定位（`healthOffsetXPx: -520`、`ammoOffsetXPx: 500` 等）
- 没有任何 `Widget` 组件做边缘对齐，全部是 `setPosition`

**问题**

| 场景 | 后果 |
|---|---|
| 21:9 带鱼屏 | 左右留黑边，HUD 挤在中间 1280 宽的区域里 |
| 4:3 或竖屏 | 上下留黑边 |
| 笔记本 1440×900（16:10） | 上下黑边，血量/弹药距离屏幕边缘忽远忽近 |
| 移动端浏览器（PRD 列为兼容目标） | 基本没法看 |

对青少年学员来说，**大概率是各种笔记本电脑，屏幕比例五花八门**。课堂演示时投影仪也常是 16:10。

**建议**

1. HUD 根节点分区（`TopLeft` / `TopRight` / `BottomLeft` / `BottomRight` / `Center`），每个分区挂 `Widget` 做边缘对齐，元素相对分区定位
2. `presentation.json` 的偏移量从「屏幕中心绝对坐标」改为「距离所属边缘的距离」，语义更稳
3. 分辨率策略改用 `FIXED_HEIGHT`（横屏游戏更合适）或保留 `SHOW_ALL` 但用 Widget 兜住边缘元素
4. **同步修掉 `Boot.scene` 里 960×640 与代码 1280×720 的不一致**（归属 Mac 端）

## 2. P1 级：手感与观感，玩家会明确感觉到

### P1-1 敌人和队友没有朝向，永远是正立方体

**现状**

- `enemy-renderer.ts:222-256` 只设置 `position` 和 `scale`，从不设 `rotation`
- `AllyState` 协议里**已经有** `aimYaw` / `aimPitch` 字段（`shared/protocol.ts:186-187`），客户端完全没用
- `EnemyState` 协议里**没有**朝向字段

**问题**

所有单位都是轴对齐的方块，看不出面朝哪里。M4 接入 Billboard 后 Billboard 恒朝摄像机，但**朝向信息依然缺失** —— 玩家无法判断「这个日军是在冲锋还是在瞄我」，而这正是 PRD 8.4 要求的「开火预警」体验的一半。

**建议**

- **需要协议扩展**（服务端归属，Debian 端）：`EnemyState` 增加 `facingYaw: number`
- 客户端把队友的 `aimYaw` 用起来，方块先绕 Y 轴旋转，M4 换成 Billboard 时改为控制立绘的 `left/right/back` 三态贴图切换（军服素材已有 front/back/side 三张图，**正好对应**）
- 这条建议**属于 `shared/protocol.ts` 改动，按 AGENTS.md 铁律 11 需要双机协商**，建议写进 `OPEN-QUESTIONS.md` 的协议变更提案区

### P1-2 插值只做了位置，没做朝向；且 `entityPositionSmoothing` 配了但没用

**现状**

- `presentation.json:19` 定义了 `entityPositionSmoothing: 12`
- `game-config.ts` 声明了这个字段并做了校验
- **全项目没有任何一处实际读取它**（已全局搜索确认）
- 敌人/队友的位移用的是 `tween(...).to(1/tickRateHz, ...)`，即 50ms 线性补间

**问题**

1. 死配置项容易误导后续开发者，也违反「配置驱动」的初衷 —— 要么用起来，要么删掉
2. `tween` 每帧对每个敌人 `stopAllByTarget` + 新建 `tween` + `new Vec3()`。同屏 40 个敌人、20Hz 快照 = **每秒 800 次 tween 创建 + 1600 个 Vec3 分配**。AGENTS.md 第 5 节明确禁止「20Hz 主循环里分配大量临时对象」，这里客户端侧踩了同样的坑
3. 网络抖动时 tween 会被中途打断重设，产生轻微顿挫

**建议**

改为在 `update(dt)` 里做指数平滑（复用已有的 `entityPositionSmoothing`），和 `first-person-controller.ts:126-136` 摄像机的做法保持一致。顺带消灭每帧的对象分配。

### P1-3 死亡表现过于简陋

**现状**（`enemy-renderer.ts:111-130`）

敌人死亡 = 方块 Y 轴缩放到 0，0.5 秒。视觉上是「凭空压扁消失」。

**PRD 6.4 明确要求**：阵亡 = 静态图 + 倒地旋转 90° + 淡出。

**建议**

- 至少改成「绕 X 轴旋转 90° + 透明度淡出」，代码量差不多，观感差距很大
- 需要给材质加 `USE_ALPHA` 或改用支持透明的 effect，M4 前先把管线打通
- 击杀感是射击游戏的核心正反馈，这块投入产出比极高

### P1-4 开火预警是「敌人身上多一个橙块」

**现状**（`enemy-renderer.ts:181-187, 270-282`）

`FireWarning` 是一个子立方体，放在 `(0, 0, -0.6)` 位置，激活时显示橙色方块。

**问题**

- 位置固定在局部 -Z，但**敌人没有朝向**（见 P1-1），所以这个「枪口焰」的方向和敌人实际射击方向无关
- 方块形状不像枪口焰，像敌人身上长了个瘤
- 0.35 秒预警是核心防御机制（PRD），表现不清晰会让玩家觉得「莫名其妙就掉血」

**建议**

- 短期：改成朝向玩家的小尺寸 Billboard 四边形 + 高饱和黄橙色 + 快速缩放动画
- 中期：M4 接入粒子系统
- 配合 P1-1 的朝向字段，让预警出现在敌人「面朝玩家的那一侧」

### P1-5 音效全是 `AudioContext` 方波蜂鸣

**现状**

- `weapon-view.ts:158-183`：105Hz 方波，55ms —— 这是「哔」，不是枪声
- `m1-hud.ts:389-416`：520Hz 正弦波当喊话提示音

**挑剔用户视角**：射击游戏 90% 的爽感来自音效。方波蜂鸣会让整个游戏听起来像 1980 年代的小霸王。

**建议**

- PRD 6.5 已列「枪声音效」为 P0 待补素材，**但这块目前没有任何进度**
- 建议在 M4 之前先接 1 个免费枪声 + 1 个命中闷响 + 1 个喊话提示，哪怕先用 CC0 素材占位
- 每次 `playFire` 都会 `context.resume()`，高频开火时是无谓开销；建议改为只在首次用户手势时 resume 一次
- **注意**：`weapon-view.ts` 和 `m1-hud.ts` 各自 new 了一个 `AudioContext`，浏览器对同页面 AudioContext 数量有限制，建议合并成一个共享的音频管理器

### P1-6 第一人称武器是两个矩形

**现状**（`weapon-view.ts:100-120`）

用 `Graphics` 画了两个矩形（枪身 + 枪管）+ 一个圆形枪口焰。

**建议**

- 这块 M4 会换成 `武器素材/liaoshi13/right.png`，**但现在的后坐动画方向可能是错的**
- `playFire` 的后坐是 `x + 18, y - 18`，即向右下移动。第一人称武器后坐应该是**向后（视觉上向右下 + 略微向上抬枪口）+ 轻微旋转**
- 建议在 M4 换图时同步重做后坐曲线：快速后坐（0.05s）+ 缓慢回位（0.15s），而不是现在的等时间对称补间（`weaponRecoilSec` 两段都是 0.07s）
- `playReload` 用 `eulerAngles` 的 z 轴转 `-weaponRecoilPx`（18 度），把「像素」当「角度」用，是配置语义混用，建议单独加 `reloadTiltDeg`

| P2-4 | 准星是纯白细线，1080p 下几乎看不见 | `m1-hud.ts:418-436` | 加 1px 深色描边（画两遍，先粗深后细白），这是 FPS 标配 |
| P2-5 | 受击红晕是一个矩形描边 | `m1-hud.ts:438-455` | 硬边框不像「渐晕」，建议用带 alpha 渐变的贴图或多层递减 alpha 矩形 |
| P2-6 | 大量 `setTimeout` 做视觉计时 | `m1-hud.ts:284/306`、`enemy-renderer.ts:99`、`ally-renderer.ts:87` | 页面切后台时 `setTimeout` 会被节流，导致颜色卡在高亮态。建议统一用 `scheduleOnce` 或 tween |
| P2-7 | 错别字「矄准」 | `m1-hud.ts:32` | 改为「瞄准」 |
| P2-8 | 队友面板是纯文本行 | `m1-hud.ts:203-242` | PRD 8.2 画的是血条 `██████ 82`，当前是 `82/100` 文字。血条比数字直观得多，`Graphics` 画矩形即可 |
| P2-9 | 三路威胁指示器用 `●` 字符重复 | `m1-hud.ts:261-269` | 中文字体下圆点间距不均；建议用 `Graphics` 画圆点，并给 A/B/C 三路配不同色相 |
| P2-10 | `data-langyashan-m1` 和 `data-langyashan-m2` 写入完全相同的 JSON | `m1-game.ts:346-353` | 冗余，每次快照序列化两遍完整状态。20Hz × 2 = 每秒 40 次 JSON.stringify |
| P2-11 | 类名 `M1Game` / `M1Hud` 已经承载到 M2/M3 内容 | `core/`、`ui/` | 里程碑代号写进类名，越往后越别扭。建议 M3 收尾时统一改名为 `BattleGame` / `BattleHud` |
| P2-12 | 无 `resize` 监听 | 全局 | 浏览器窗口缩放/全屏切换时 HUD 布局不会重算 |

## 4. 给两端 Codex 的分工建议

按 `docs/COLLAB.md` 的归属划分：

### 💻 Mac 端（客户端表现层，独立可做）

**M3 内建议顺手做掉**（低成本高收益）：

**M3 与 M4 之间建议插入一个「视觉基线」小阶段**：

- P1-3 死亡表现（旋转倒地 + 淡出）

## 5. 不建议现在做的事（避免过度设计）

| 事项 | 理由 |
|---|---|
| 战斗局内加煤油灯 / 火把等人造光源 | **史实不符**。25 日战斗全程在白天（清晨 6 时至太阳偏西），山顶阵地无人造照明。人造暖光只用于部署期的 24 日深夜过场 |
| 把手榴弹埋雷做成实际玩法 | PRD 未定义，属自行发挥（违反铁律 1）。仅作部署期叙事表现 |
| 引入 UI 框架 / 图集打包 | 当前 UI 元素数量还没到需要工具链的规模，M4 之后再评估 |
| 后处理特效（Bloom / 色调映射） | Web 端性能预算紧张，PRD 红线是 PC ≥ 50 FPS，先保帧率 |
| 逐帧角色动画 | PRD 6.4 已明确 v1.0 用 tween 模拟，不要自行升级 |
| 重写渲染层 | 现有结构（Renderer 分层 + 对象池）是对的，只需要补光照和材质，不要推翻 |
